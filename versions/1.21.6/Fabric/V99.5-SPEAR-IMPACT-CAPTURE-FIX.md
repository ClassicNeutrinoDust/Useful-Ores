# V99.5 — spear impact capture + movement rework

## Root cause

The server-only kinetic loop was evaluating `LivingEntity.getDeltaMovement()` after
movement/collision resolution. When the player sprinted into the target, the collision
could reduce/redirect that velocity before the spear test ran. The result was a missed
kinetic condition. The later standing/crosshair test succeeded because the target was
again explicitly detectable.

## Reference implementation used

The supplied Accurate Spears 2.2 Fabric 1.21.10 jar uses two separate packets:

- a velocity packet sent every START_CLIENT_TICK using `(currentPos - previousPos) * 20`
- an attack packet sent while charging when the crosshair is on a valid living entity

Its server damage routine uses the stored client velocity for the relative-speed test.

## V99.5 architecture

`START_CLIENT_TICK`
→ capture pre-movement displacement * 20
→ capture current crosshair living target UUID
→ send `SpearChargeFramePacket`
→ server validates current spear-use state and target
→ compute attacker speed from captured pre-collision velocity
→ project target motion onto view vector
→ relative speed
→ kinetic damage immediately on the impact frame

The old server-only kinetic damage call from `SpearItem.onUseTick` is now state-only,
preventing a post-movement duplicate calculation.

## Sprint movement

The movement mixin now intercepts the actual `applyMovementSpeedFactors` stage plus the
`canSprint` gate, rather than only trying to patch downstream sprint-stop logic.
